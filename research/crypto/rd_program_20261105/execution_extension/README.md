# RD1 隔离执行适配：开发中

接续用户新建的持续目标，补原生订单生命周期与原子风险预留；不改写冻结 RD1、P1 输入、因果诊断预算或运行服务。

本阶段 `reservations.py` 实现预留层。每个隔离账户有单写者文件锁和进程内互斥锁，先让冻结 RD1 对真实快照检查，再把未决预留作为额外挂单计算余额、gross/net、单币、相关簇和数量上限。虚拟挂单不写入 RD1 的真实快照游标，避免同游标内容冲突。预留写前日志和主状态持久化成功后才返回记录。

相同请求 ID、相同提案只返回旧记录；不同提案复用 ID 拒绝。返回记录始终 `submission_authorized=false`，包括重启后查询旧请求；它不是可调用交易所的授权 token。持久化异常后实例不可再用。中断于日志提交与主状态替换之间时，重开恢复日志，仍保留风险占用。

当前保留全部未决数量，没有释放、提交、确认或执行 API。订单已实际进入快照时可能保守重复占用，尚不适合驱动交易。下一阶段须实现：提交前重新检查新鲜快照与风险锁、持久 single-attempt 状态、确认与未知结果、部分成交的预留转移、撤单竞态、最终成交／持仓对账。超时、未见订单、重启均不能单独证明请求未成交。原生 `freqtradebot.py` 的 `execute_entry`、`handle_cancel_enter`、`update_trade_state` 是待衔接的生命周期入口，当前没有修改或调用它们。

已通过 10 项合成单元／故障测试（`test_reservations.py`），覆盖并发、幂等、冲突、簇限制、多空 gross、重启、单写者、写盘异常、日志恢复、缺报价和返回对象隔离。测试不是真实行情、沙盒或生产验证，没有金融回测或订单。

## 生命周期桥接增量

`lifecycle.py` 在预留层上增加隔离重放票据与 CCXT 形状的订单回报核对，仍没有网络或真实提交接口。`claim_for_replay` 在新鲜快照上重验 RD1 和全部未决预留，持久化一次尝试后返回稳定 clientOrderId；返回成功前崩溃或结果未知时，不允许再次领取。过期市场输入会拒绝领取，不靠旧预留绕过风险锁。

回报必须匹配 clientOrderId、交易对、方向、原始数量及限价；累计成交不能回退，事件 ID 幂等且冲突拒绝。`observed_at` 是调用方提供的真实接收时刻，缺失时拒绝，不能从订单创建时间推算。跟随回报的账户快照必须更新游标、对账通过且新鲜。open 状态只有在剩余挂单和已成交持仓都精确对应时，才在**该份快照**中停止重复计算预留；换快照后重新核对，否则恢复保守占用。

原生代码 `execute_entry` 会处理 expired/rejected 的部分成交，所以 terminal 状态并不等于零成交。适配层只在账户已表示累计成交持仓、剩余挂单已不开放时解除预留。它不会删除真实持仓或释放持仓风险，随后入场仍须经过 RD1。撤单竞态允许累计成交增加，拒绝把旧成交量当最终状态。

当前累计 **23 项合成测试通过**（10 项预留、13 项生命周期），新增覆盖重启后未知结果、领取持久化失败、过期领取、部分成交、部分到期、零成交拒绝、缺失挂单、回报冲突、成交回退、撤单竞态与全部成交。`verification.json` 是上一提交的历史 10 项证据；`lifecycle_verification.json` 保存当前源码身份与 23 项结果，不回写历史收据。

仍待完成：真实原生对象到这些输入的严格转换、逐事件重放执行器和完整进出场归因。目前同一 campaign 在入场回报对账前已有退出时，持仓不再等于累计入场量，会拒绝释放，需完整成交账本后续解决。调用方给出的原始事件／接收时刻尚未认证；不能把这组手工合成回报称为原生端到端或历史验证。没有改动 `freqtradebot.py`、运行配置、数据库或服务。

## 原生对象和 campaign 成交桥接增量

`native_evidence.py` 新增原始回报信封与 native Order 对照。测试实际调用本仓库 `Order.parse_from_ccxt_object` 和 `to_ccxt_object`，核对保留的订单身份、状态、方向、数量和限价；没有实例化交易所或数据库会话。原生转换确实不保留 clientOrderId 和首次接收时刻，minified 导出更缺少订单身份；因此必须另存原始回报及明确接收时刻，缺失即拒绝。不得把原生代码回填的当前 order_update_date 或 order_filled_date 当历史接收证据。JSON 原生浮点采用最短十进制表示进行比对，明确不是恢复交易所原始十进制精度。

`replay_campaign` 对每个入场订单的全部部分成交和对应退出逐笔重建剩余数量、交易现金流与费用；相同成交 ID 幂等，冲突拒绝，方向错误、超额退出、时间倒退拒绝。行情、资金费、保证金和完整账户 NAV 不在这个函数的核算范围。费用须明确提供 quote currency 金额，不推测缺失费用或币种换算。

生命周期对账现可接收 `campaign_fills`：累计入场量须等于订单回报，扣除全部退出后剩余量须等于账户持仓，成交不得早于领取尝试或晚于快照接收边界。由此覆盖先部分成交、再完全退出、最后收到入场撤单确认的路径。收到终态后保留完整成交列表/hash 输入；真实来源完整性仍需外部证据，不能凭本地自洽自动证明。

当前 **32 项合成检查通过**（含实际 native Order 方法调用），记录在 `native_evidence_verification.json`。旧 10/23 项收据仍是各自提交的历史证据。下一步继续核验可取得的历史数据及原始事件收据，补隔离重放运行登记；这些进展尚未解除 F1/F2 的经济准入，也没有启用交易执行。

## 全账户算术重放增量

`account_replay.py` 从明确的 1000 USDT、空仓初态接收完整有序事件。现货按现金与持仓记账；合约按 wallet、已实现价格损益、未实现 mark 损益、应计／已结算资金费和退出储备记账。保证金不作为损失重复扣除。部分成交更新加权成本，部分退出保留剩余成本；反向穿零要求拆成明确的平仓和新 campaign。费用必须显式提供，不以缺失值代替零。

事件 ID 幂等、冲突拒绝；声明的账户 sequence 必须连续。同刻含成交的金融事件若没有明确顺序合同，会拒绝继续，不替调用方选择资金费先后顺序。应计资金费进入 NAV，结算时从应计移除并转入 wallet，净值不重复减少；新事件 ID 重复结算同 funding ID 也拒绝。无效事件先在内存副本上处理，不污染此前状态。

这些函数仅检查输入之间的一致性：`source_ordered` 是调用方必须举证的合同，不是程序认证了真实交易所顺序；`captured` 标签也不是历史完整性证明。估值要求同期 spot bid/futures mark 和显式 funding 完整性标志；不从 OHLCV 生成资金费、行情可得时间或私人账户事件。返回可与 RD1 比对的 Position 对象，仍无真实下单功能。

新增 10 项账本测试，当前合计 **42 项合成检查通过**：浮亏、部分退出、多次成交成本、空头资金费收入、结算去重、现货现金、事件间隙／冲突、未知同刻顺序、缺行情和未来事件，以及与冻结 RD1 权益核算的一致性。`account_replay_verification.json` 是该版本的源码收据；前面各阶段的数量和收据保持历史含义。测试的费用数值只是算术夹具，未注册任何金融收益候选。

还需把这些部件组成有输入证据清单的隔离重放入口，验证原生执行生命周期接缝及故障场景；完整历史数据访问、时点规则和实际账户事件证据仍是经济准入依赖。旧 paper 与真实账户均未修改。
