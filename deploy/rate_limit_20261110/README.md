## 根因与改动边界

7个模拟盘与2个实盘通过同一本地代理分别采集行情，WebSocket关闭。CCXT实例限速没有约束跨进程总量；原生临时错误重试在收到418后仍继续触发请求。日更选币另有4个并行HTTP读取任务。原生合约日志在00:00:31记录429、00:00:41记录418，最近5分钟曾有3450条带时间戳的418记录；日志条数不是精确HTTP请求数，且不能唯一归因到某个进程。

依据 [Binance IP限额规则](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/general-info) 与 [CCXT 实例限速边界](https://github.com/ccxt/ccxt/wiki/Manual#notes-on-rate-limiter)，扩展本项目原生 freqtrade/exchange/exchange.py 的客户端初始化，安装 freqtrade/exchange/request_guard.py。未修改已安装CCXT包；不是独立交易执行器，也未把本地扩展标成上游官方功能。

上游对象与原始文件哈希仍保留在 deploy/upstream-source.json。deploy/release.json 的 upstream_local_extensions 单独登记原生入口变动、原始哈希、本地哈希和理由；新增模块及部署策略亦固定哈希。没有把源码改动藏进 metadata exceptions。

## 实际保护

- 所有本部署 Binance 客户端共用私有SQLite状态，跨现货、合约、同步、异步、模拟与实盘合并限额：每分钟900权重、180次请求，最多4个请求同时进行。按权重平滑准入；保留CCXT原有限速。该额度是保守的本地预算，不是交易所额定上限。
- 收到418/429，在所有进程间持久保存冷却期限，尊重错误中的封禁时间及 Retry-After，并增加5秒缓冲。无期限的418至少冷却15分钟、429至少2分钟；后续成功响应不能缩短已有冷却。服务重启不能清掉期限。
- 请求在获准发送后才生成签名；如果另一在途请求刚报告封禁，再次在实际传输前拦截。关闭CCXT内部绕过准入的自动重试，原生重试仍必须经过共享准入。没有更换代理、IP或API来绕过封禁。
- 公开市场元数据缓存1小时；完全相同的公开K线请求缓存10秒，并有跨进程请求合并。接口来源、参数及K线时间边界参与键值，不跨收盘边界复用。不缓存账户、余额、订单、成交、ticker或盘口；崩溃留下的缓存所有权有期限，重复所有者不能覆盖更新的结果。
- 原生日更选币的4个线程继续保留，但公共请求进入同一预算。已提交的实盘检查、现货运行核对、逐笔成交核对等辅助GET读取也接入；辅助会话不允许 Binance 写请求，并限制签名后等待时间，额度不足时失败返回。工作区未提交的旧准备脚本不属于已部署入口。
- 读取IP已用权重响应头，达到保守余量线时冷却至下一个分钟窗口。SQLite或策略损坏时失败关闭；不因读取状态失败退回无保护请求。预算外的同公网出口其他使用者仍可能触发交易所限制，因此无法保证永不限流。
