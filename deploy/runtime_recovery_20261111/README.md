# 实盘运行恢复与有限重试

用户于2026-11-11明确要求“代理不稳定可能要有重试逻辑，修复上线”。本次修复既有现货、永续实盘的传输恢复，不更改策略、币池、手续费、99U预算、100U投入上限及逐仓3倍设置。模拟盘继续停用。

## 已确认的故障

永续在北京时间2026-11-11 07:30:55异常退出。原生退出检查读取盘口时，本地共享请求保护模块在`INSERT INTO leases`写入SQLite失败，抛出未被原生临时错误路径处理的`sqlite3.OperationalError: unable to open database file`。通知同时曾返回503。确认的是本地存储访问失败，尚未确定底层文件系统原因，不能将其直接归因为代理故障。检查时数据库完整性正常，DOT空单仍在交易所。

## 修复

- 在现有本地扩展`freqtrade/exchange/request_guard.py`内，对BUSY、LOCKED、CANTOPEN、IOERR、FULL等存储故障重开完整事务，最多重试2次，退避0.25/0.75秒。事务失败时先回滚、关闭连接；耗尽后转为`ccxt.ExchangeNotAvailable`子类，由原生交易所模块映射为`TemporaryError`，进入原生Worker暂停后重试。持续故障时禁止发送请求，不重建或清空状态库，不绕过限流。损坏、SQL错误等非暂时故障不被伪装为恢复成功。
- 同步与异步原生CCXT GET传输发生网络异常时，最多重试2次，退避0.5/1秒；每次重新申请共享预算并重新签名。418/429、权限和认证失败不在本层重试。保留跨进程冷却；内存也保留未能持久化的封禁期限，数据库恢复后重新发布。
- POST/PUT/DELETE不在本层重放。已收到的订单响应或原始超时不会被限流计数、租约清理或公共缓存写入故障覆盖；订单不确定状态仍由原生流程核对。清理失败的租约按原45秒期限失效。
- 两个既有实盘改由`io.freqtrade.live.{spot,futures}` LaunchAgent托管，异常退出后自动恢复，两次启动至少相隔60秒。正常退出不强制重启。每次仍通过原有源码/配置哈希、资金约束及单实例文件锁检查；使用原数据库、凭据和利润缓存。进程自身持锁后写入真实PID，避免将启动请求当作运行成功。

这是原生Freqtrade流程中的本地扩展，不是上游官方新增功能。上游Worker与交易所异常映射保持原样；源码来源和本地扩展分别记录于`deploy/upstream-source.json`、`deploy/release.json`。SQLite错误码依据[官方文档](https://www.sqlite.org/rescode.html)，CCXT接口行为同时以本地安装的4.5.89源码和[上游手册](https://github.com/ccxt/ccxt/wiki/Manual)核对。
